---

Generalize SwashMoji's emoji naming/localization model so it can support a large
database of languages, while keeping the UI intentionally limited to at most
two displayed languages at once.

This is an architecture + UX extension. Preserve existing functionality and
avoid a broad visual redesign.

GOAL

Today the app effectively treats emoji names as English + Norwegian.

Refactor this into a locale-based model:

    emoji
      en -> English name
      nb -> Norwegian Bokmål name
      de -> German name
      fr -> French name
      ...

The implementation must not hardcode the product around exactly two language
fields such as english_name / norwegian_name.

Use a scalable locale-keyed representation instead.

Examples:

    names["en"]
    names["nb"]
    names["de"]

or an equivalent strongly typed structure appropriate for the current codebase.

DATA MODEL

Requirements:

- Each emoji can have zero or more localized names.
- Locale identifiers should use standard language/locale codes where practical
  (e.g. en, nb, de, fr).
- English should remain the default/fallback language.
- Existing English and Norwegian data must migrate cleanly into the generalized
  model.
- Do not duplicate translation data in separate UI-specific mappings.
- Search and display must read from the same canonical localization data.
- Missing translations must be handled gracefully.
- Do not assume every emoji exists in every language.

DISPLAY LANGUAGES

Add a user preference for which languages are shown in the UI.

The user may select:

- one display language, or
- two display languages maximum.

Do not allow more than two simultaneously.

Example:

    Languages
    Primary: English
    Secondary: Norwegian

Possible rendered result:

    🙂 slightly smiling face · smiler litt

If only one display language is selected:

    🙂 slightly smiling face

If the secondary translation is missing, show only the available primary name
without a dangling separator.

If the primary translation is missing but the secondary exists, show the
secondary.

If neither selected locale exists, fall back sensibly to English if available.

Keep the display compact and single-line where the current UI expects a
single-line status/name.

LANGUAGE SELECTION UI

Add a small preferences/settings surface for language selection.

Do not put a giant language configuration workflow into the main picker.

The UI should make this concept simple:

    Languages
    [ English      ▾ ]
    [ Norwegian    ▾ ]

or an equally compact native design.

Requirements:

- maximum two selected display languages
- prevent selecting the same language twice
- first language is primary
- second language is optional
- persist the selection using the app's existing settings mechanism
- default existing users to English + Norwegian so current behavior remains
  familiar

SEARCH LANGUAGES

Architect search separately from display, even if the first implementation uses
the same selected languages.

The code should make it possible to later support:

    Search languages:
      English
      Norwegian
      German

    Languages:
      English
      Norwegian

Do NOT tightly couple search logic to "exactly two display languages".

For this implementation, choose the simplest sensible behavior that preserves
existing search quality, but structure the APIs so search locales can be
configured independently later.

SEARCH BEHAVIOR

Emoji search should support localized names from the canonical locale database.

For example, once German data exists:

    lächeln

should be capable of matching German localized names without requiring a
separate German-specific search implementation.

Preserve:
- English search
- Norwegian search
- aliases
- emoji variants
- ranking behavior unless localization requires a minimal extension

If a match came from another locale, continue displaying results according to
the user's chosen display languages rather than necessarily switching the row
to the query language.

MAIN WINDOW STATUS

Use the generalized display-language formatter in the main SwashMoji status bar.

Do not maintain special-case English/Norwegian formatting there.

Example with English + Norwegian selected:

    slightly smiling face · smiler litt

This formatter should be reusable anywhere the UI needs a localized emoji name.

COMBINATIONS / VOCABULARY

Use the same localized-name formatting logic where appropriate in:
- main picker
- vocabulary editor
- combinations editor
- result rows
- selected emoji cards/status text

Do not fork slightly different English/Norwegian rendering logic across these
windows.

REUSABLE API

Create a small reusable localization/name layer, conceptually something like:

    GetEmojiName(emoji, locale)
    GetBestEmojiName(emoji, preferredLocales)
    FormatEmojiDisplayName(emoji, primaryLocale, secondaryLocale)
    SearchLocalizedEmojiNames(query, locales)

Exact names are up to you.

Keep UI code ignorant of how translations are physically stored.

FUTURE DATABASE SCALE

Design for tens of languages and the full emoji dataset.

Avoid:
- giant switch statements by language
- separate struct fields for every language
- language-specific search code
- duplicated locale lists across UI windows

Prefer:
- locale metadata table
- locale-keyed name data
- generic iteration/search
- one shared formatter

Do not import or generate a huge new translation dataset yet unless one already
exists in the repository. This task is primarily to make the architecture ready
for it and migrate the current English/Norwegian data.

TESTS

Add tests covering at least:

1. English only
2. English + Norwegian
3. missing secondary translation
4. missing primary but available secondary
5. fallback to English
6. duplicate display-language selection prevented
7. maximum two display languages enforced
8. search matching English localized names
9. search matching Norwegian localized names
10. formatter does not emit dangling separators
11. persisted language selection round-trips correctly
12. existing aliases/combinations remain unaffected

If practical, add a small synthetic third locale in tests to prove the
architecture is genuinely generic rather than secretly hardcoded to en + nb.

COMPATIBILITY

Preserve:
- existing saved vocabulary
- combinations
- settings
- native Win32 architecture
- keyboard navigation
- accessibility
- DPI behavior
- high contrast behavior

Do not introduce a web framework or a large external i18n dependency merely for
this feature.

IMPLEMENTATION STRATEGY

Do this in phases:

1. Generalize the data model and formatter.
2. Migrate existing English/Norwegian data.
3. Route current UI through the generalized formatter.
4. Add persisted selection of up to two display languages.
5. Generalize search APIs enough for future multi-language expansion.
6. Add tests.
7. Build and run all suites.
8. Perform one visual verification pass only.

IMPORTANT

Keep this narrow.

Do not use this task as an excuse to redesign unrelated UI, change the emoji
ranking model, rewrite storage, or import dozens of languages.

The end state should behave essentially like today's English + Norwegian app,
but the architecture should now make adding another language mostly a data
addition plus registration, not a schema/UI rewrite.
